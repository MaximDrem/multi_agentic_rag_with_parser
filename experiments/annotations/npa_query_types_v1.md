# Codebook `npa_query_types_v1`

## 1. Назначение и статус

Codebook задаёт шесть независимых multi-label признаков русскоязычных запросов к нормативным правовым актам. Он описывает формулировку и информационную потребность запроса, а не сложность для конкретной retrieval-системы и не качество возможного ответа.

На текущем этапе создаётся только этот codebook. Файл `experiments/annotations/npa_query_types_v1.jsonl` намеренно не создаётся: финальные labels требуют human review, повторной независимой разметки контрольной выборки и последующего freeze.

Все примеры ниже синтетические и служат только для пояснения правил. Они не взяты из benchmark, не являются готовыми annotations и не задают labels каким-либо реальным группам.

## 2. Единица разметки и допустимые данные

- Единица разметки — один normalized `query_group`. После human review ожидается ровно 556 строк, по одной на группу.
- Representative query выбирается по минимальному `source_row`; его стабильный ID записывается в `representative_question_id`.
- Аннотатор использует текст representative query и, при необходимости понять общую нормализованную форму, тексты вопросов той же группы. Нельзя смешивать разные группы.
- Все шесть labels оцениваются независимо и принимают только `true` или `false`. Сочетания labels разрешены, включая сочетание `other_unclear=true` с любым другим label.
- Не использовать retrieved IDs, candidate pools, системные ответы, prompts, scores, qrels, gold/evidence labels и будущие метрики. Не выводить label из того, что нужный документ якобы был найден или не найден.
- Не исправлять исходный вопрос и не доинтерпретировать его по внешнему ответу. Существенная неоднозначность отражается через `other_unclear` и confidence.
- `notes` содержит только краткое обоснование по тексту запроса. В нём не должно быть retrieved IDs, system outputs или метрик.

## 3. Labels

### 3.1. `exact_reference`

**Определение.** В запросе есть точный указатель на НПА или его структуру: официальное либо общеупотребительное точное название, номер и/или дата акта, статья, пункт, часть, приложение или иной однозначно обозначенный структурный элемент.

**Положительные примеры.**

- «Какая ответственность предусмотрена статьёй 236 ТК РФ?» — указаны статья и точное сокращённое название кодекса.
- «Что изменил Федеральный закон от 13.07.2020 № 193-ФЗ?» — указаны дата и номер акта.
- «Как применяется пункт 3 статьи 81?» — есть точный структурный указатель даже без названия документа.

**Отрицательные примеры.**

- «Какая ответственность предусмотрена за задержку зарплаты?» — нет точного указателя на акт или структуру.
- «Какие выплаты положены при увольнении 15 марта 2024 года?» — дата обозначает событие, а не реквизит НПА.
- «Что говорится об этом в законе?» — общее слово «закон» не идентифицирует акт.

**Пограничные случаи.**

- Общепринятые точные сокращения вроде «ТК РФ», «НК РФ» или «44-ФЗ» засчитываются.
- Названия «гражданский кодекс» без реквизитов достаточно, если в контексте оно однозначно обозначает конкретный кодекс; неясность остальной потребности отражается отдельно через `other_unclear`.
- Число, дата или слово «статья» сами по себе не дают `true`: должен быть указатель на документ или его структуру, а не сумма, срок, дата события или бытовое упоминание.
- Неточность предполагаемого реквизита не проверяется по retrieval. Если указатель сформулирован как точный, label выставляется по тексту запроса; сомнение в смысле можно отметить в `notes`.

### 3.2. `lay_paraphrase`

**Определение.** Информационная потребность выражена преимущественно бытовым, разговорным или непрофессиональным описанием ситуации без точной юридической терминологии. Важен способ формулировки, а не предполагаемая юридическая простота темы.

**Положительные примеры.**

- «Босс не отдал расчёт после увольнения, куда жаловаться?» — разговорное описание участников и ситуации.
- «Что делать, если сосед затопил квартиру и не хочет платить за ремонт?» — бытовое описание вреда и требуемого действия.

**Отрицательные примеры.**

- «В какой срок работодатель обязан произвести окончательный расчёт при расторжении трудового договора?» — использована профессиональная юридическая формулировка.
- «Каков порядок возмещения вреда, причинённого имуществу вследствие залива квартиры?» — формальная терминология.

**Пограничные случаи.**

- Конструкция «что делать, если…» сама по себе не является достаточным признаком: оценивается вся формулировка.
- Отдельный юридический термин не исключает label, если основная ситуация всё равно описана разговорно и непрофессионально.
- `lay_paraphrase` может сочетаться с `exact_reference`, например когда бытовой вопрос содержит точную ссылку на акт.
- Опечатки, короткий запрос или отсутствие знака вопроса не делают формулировку автоматически бытовой.

### 3.3. `multi_issue`

**Определение.** В одном запросе различимы несколько правовых подвопросов, требующих самостоятельного рассмотрения: отдельные требования, действия, последствия или правовые положения разных субъектов. Для `true` недостаточно нескольких фактов одной ситуации.

**Положительные примеры.**

- «Можно ли расторгнуть договор в одностороннем порядке и кто должен вернуть аванс?» — два самостоятельных подвопроса.
- «Какие документы нужны для регистрации и в какой срок их должны проверить?» — отдельно требования к документам и срок проверки.

**Отрицательные примеры.**

- «В какой срок должны вернуть аванс после расторжения договора?» — расторжение является условием одного вопроса о сроке.
- «Может ли работник с десятилетним стажем и двумя детьми получить отпуск?» — несколько обстоятельств, но один различимый правовой вопрос.

**Пограничные случаи.**

- Перечень однотипных элементов внутри одного вопроса не создаёт `multi_issue`.
- Упоминание нескольких субъектов даёт `true`, если для них требуется отдельно определить права, обязанности или режимы; если субъект является лишь условием одной нормы, ставится только `applicability_conditions`.
- Несколько грамматических предложений не гарантируют несколько правовых вопросов. Нужна содержательная самостоятельность подвопросов.
- `multi_issue` не означает обязательно multi-hop retrieval и не зависит от расположения evidence в corpus.

### 3.4. `applicability_conditions`

**Определение.** Для ответа существенны условия применимости нормы: категория субъекта, срок, территория, исключение, порог, стадия процесса или иное обстоятельство, определяющее, применяется ли правило к описанной ситуации.

**Положительные примеры.**

- «Положён ли дополнительный отпуск работнику, который трудится во вредных условиях меньше года?» — значимы категория работника и продолжительность работы.
- «Распространяется ли это требование на ИП без наёмных работников?» — прямо поставлен вопрос о категории субъекта и исключении.

**Отрицательные примеры.**

- «Как называется документ, подтверждающий регистрацию?» — запрошено общее сведение без условий применимости.
- «Какой орган выдаёт разрешение?» — нет существенного сценария, исключения, порога или иного условия применения нормы.

**Пограничные случаи.**

- Любое обстоятельство в запросе не считается условием автоматически: оно должно влиять на выбор или применимость нормы.
- Дата события может быть условием применимости, но не становится от этого `exact_reference`.
- Один вопрос с несколькими условиями обычно имеет `applicability_conditions=true`, но `multi_issue=false`.
- Общие вопросы «при каких условиях», «на кого распространяется», «какие есть исключения» относятся сюда даже без подробного сценария.

### 3.5. `cross_reference_multi_document`

**Определение.** Для ответа требуется связать нормы или документы: пройти по явной отсылке к другой норме, установить соотношение положений нескольких НПА либо объединить требования разных документов в одну правовую связь.

**Положительные примеры.**

- «Как соотносятся требования ТК РФ и указанного постановления о дополнительном отпуске?» — необходимо установить соотношение двух актов.
- «На какой акт ссылается пункт 4 этой статьи и какое дополнительное требование он вводит?» — нужно пройти по явной отсылке и связать нормы.

**Отрицательные примеры.**

- «Что установлено статьёй 25 указанного закона?» — есть точный указатель, но нет необходимой связи с другой нормой.
- «Назови срок уведомления по ТК РФ и отдельно срок подачи заявления по НК РФ.» — упомянуты два акта, но связи между нормами нет; при самостоятельности подвопросов возможен только `multi_issue`.

**Пограничные случаи.**

- Простое одновременное упоминание нескольких документов недостаточно: должна требоваться связь, сравнение норм или совместное применение.
- Явная внутридокументная отсылка засчитывается, если без обращения к указанной связанной норме нельзя ответить на вопрос. Одиночная ссылка на статью как предмет вопроса сама по себе отсылкой между нормами не является.
- Не предполагать необходимость другого документа только потому, что тема обычно регулируется несколькими актами. Потребность должна следовать из текста запроса.
- Label не выставляется по тому, сколько документов оказалось в qrels или в выдаче.

### 3.6. `other_unclear`

**Определение.** Формулировка неполна, внутренне противоречива или настолько неоднозначна, что аннотатор не может уверенно определить информационную потребность. Это самостоятельная оценка неопределённости, а не категория-остаток.

**Положительные примеры.**

- «А как насчёт статьи?» — без контекста непонятны акт, статья и требуемое действие.
- «Подскажите по 44-ФЗ, что там у нас?» — акт указан, но потребность неясна; одновременно допустимы `exact_reference=true` и `other_unclear=true`.

**Отрицательные примеры.**

- «Что делать, если соседи шумят ночью?» — потребность понятна, хотя нет точного юридического указателя.
- «Какой общий порядок государственной регистрации права?» — запрос широкий, но вполне определённый.

**Пограничные случаи.**

- Не выставлять `other_unclear=true` автоматически всем запросам без первых пяти labels. Ясный запрос может получить `false` по всем шести labels.
- `other_unclear` может сочетаться с любым другим label: часть формулировки может быть точной, а общая потребность — неясной.
- Сложная тема, редкая терминология, широкий вопрос, опечатки или нестандартная грамматика сами по себе не означают неопределённость.
- Если возможны две равноправные трактовки, выбирающие разные правовые действия, обычно ставится `true`; одна очевидная трактовка при стилистической неточности — нет.

## 4. Confidence и формат будущей записи

`annotation_confidence` выражает уверенность аннотатора в присвоении всей совокупности labels по тексту запроса:

- `high` — критерии применяются прямо, существенной неоднозначности нет;
- `medium` — есть пограничный случай, но одна трактовка заметно предпочтительнее;
- `low` — остаётся существенная неоднозначность или нехватка контекста. Это часто сопровождается `other_unclear=true`, но не заменяет независимую проверку этого label.

После human review каждая строка JSONL должна иметь ровно следующую структуру:

```json
{
  "query_group": "...",
  "representative_question_id": "...",
  "labels": {
    "exact_reference": false,
    "lay_paraphrase": true,
    "multi_issue": true,
    "applicability_conditions": true,
    "cross_reference_multi_document": false,
    "other_unclear": false
  },
  "annotation_confidence": "high",
  "annotator": "human_a",
  "notes": "",
  "review_status": "human_reviewed"
}
```

Пример показывает только схему и не является разметкой реальной группы. Неизвестные labels, null и пропущенные boolean поля недопустимы.

## 5. Human review и независимая повторная разметка

1. До разметки аннотатор изучает codebook на синтетических примерах. LLM может подготовить draft labels, но человек обязан проверить каждую финальную строку и принять решение самостоятельно.
2. Основная разметка выполняется до просмотра full quality results. Аннотаторы не получают qrels, retrieval/ranking outputs, системные ответы и subgroup metrics.
3. Контрольная выборка выбирается детерминированно от `query_group + seed` до начала повторной разметки и до открытия quality results. Состав выборки фиксируется.
4. Независимо повторно размечается не менее 20% groups и не менее 100 groups, что больше при доступности. Для 556 groups 20% после округления вверх составляет 112 groups, поэтому требуемый минимум — **112**, а не 100.
5. При двух аннотаторах второй работает независимо, без доступа к labels, notes и confidence первого. Оба применяют одну версию codebook.
6. Если повторную разметку выполняет тот же человек, это обозначается только как audit agreement. Такой аудит не называется межэкспертной надёжностью и не заменяет Cohen's kappa для двух независимых аннотаторов.
7. Технические ошибки схемы исправляются без изменения смысловых labels. Любое содержательное уточнение codebook до freeze применяется единообразно ко всем затронутым группам; контрольная выборка при необходимости пересматривается обоими аннотаторами независимо.

## 6. Cohen's kappa и разрешение разногласий

Для двух независимых аннотаторов согласованность вычисляется на исходных, ещё не adjudicated binary labels контрольной выборки:

- отдельно для каждого из шести labels сообщаются число пар `n`, confusion counts, raw agreement и Cohen's kappa;
- вычисляется `κ = (p_o - p_e) / (1 - p_e)`, где `p_o` — наблюдаемая доля совпадений, а `p_e` — ожидаемая доля совпадений по маргинальным распределениям двух аннотаторов;
- нельзя заменять шесть per-label значений одним pooled kappa или сравнивать labels после adjudication;
- если `1 - p_e = 0`, kappa математически не определена: записывается `null` с явной причиной, а не ноль или единица; raw agreement и распределение всё равно сообщаются;
- дополнительно полезно указать prevalence каждого label у каждого аннотатора, чтобы интерпретировать нестабильность kappa при редких labels, но не подбирать labels для повышения согласия.

После фиксации исходных пар и расчёта kappa разногласия разрешаются по codebook обсуждением аннотаторов или заранее назначенным человеком-арбитром. Для каждой изменённой группы сохраняются исходные решения и краткая человеческая причина финального решения. Нельзя разрешать спор по qrels, найденным chunks или качеству системы.

Машинный gate использует раздельные файлы из config: исходный `primary_independent` для всех 556 groups, исходный `secondary_independent` ровно для 112 control groups, final `labels` и `adjudications`. Kappa вычисляется только по первым двум, а не по final. Для каждого разногласия обязательна запись:

```json
{
  "adjudication_id": "group_0000:multi_issue",
  "query_group": "group_0000",
  "label": "multi_issue",
  "primary_label": false,
  "secondary_label": true,
  "final_label": true,
  "adjudicator": "human_c",
  "reason": "Краткая причина по codebook",
  "review_status": "human_reviewed"
}
```

Записи создаются для всех A/B disagreements и для каждого расхождения final с primary, включая согласованные control pairs и groups вне control sample. Для groups вне control sample `secondary_label` равен `null`. Это применяется и когда final совпал с одним из исходных решений. `annotations-validate` проверяет идентичность исходных labels, полноту причин и соответствие final; затем сохраняет `reliability`. Любое последующее изменение входов делает reliability stale и блокирует freeze.

## 7. Freeze

- До full scoring проверяются 556 уникальных `query_group`, корректность representative IDs, отсутствие unknown groups и полнота шести boolean labels.
- Финальные annotations проходят human review; disagreements контрольной выборки разрешены и задокументированы.
- Codebook и финальный JSONL замораживаются вместе; их SHA-256 вычисляются и записываются в freeze manifest до full scoring.
- После freeze нельзя перестраивать labels по subgroup effects, успешным или неуспешным запросам и нельзя незаметно менять codebook.
- Общая ошибка разметки требует остановки, новой версии protocol/annotations и повторной согласованной разметки всех затронутых групп, а не точечной правки под желаемый результат.
